# Miku-Memory-Layer (MML) 记忆架构重构方案

## 1. 核心理念 (Philosophy)

模仿人类记忆的分层机制，将记忆从“原始对话流”中抽象为不同维度的资产，解决传统向量记忆（如 mem0）存在的“噪音多”、“无时序”、“缺乏深度画像”等问题。

*   **分层存储**：短期、中期、长期相互配合。
*   **语义压缩**：不存储每一句话，而是存储“摘要”和“事实”。
*   **画像驱动**：让 AI 拥有一个动态更新的“用户百科全书”。

---

## 2. 三层架构设计

| 层级 | 名称 | 对应 MemoryOS | 存储介质 | 逻辑说明 |
| :--- | :--- | :--- | :--- | :--- |
| **L1** | **工作记忆 (Working Memory)** | Short-Term | 内存 / Redis | 存放当前对话的原始上下文。用于维持即时对话的连贯性。 |
| **L2** | **情境记忆 (Episodic Memory)** | Mid-Term | ChromaDB (向量库) | 存放过去对话的 **Session 摘要**。当 L1 满时，压缩存入 L2。用于检索“以前聊过什么”。 |
| **L3** | **核心记忆 (Core Memory)** | Long-Term | SQLite / JSON | 存放 **用户画像 (Profile)**。通过 L1 内容定期“反思”并更新。用于确定用户的性格、偏好和身份。 |

---

## 3. 详细模块设计

### 3.1 L1: 动态缓冲区 (The Buffer)
*   **容量**：固定 15-20 轮对话。
*   **刷新逻辑 (Flush)**：
    *   当用户闲置超过 10 分钟。
    *   或者缓冲区满时。
    *   触发 **压缩存档 (Archive)** 与 **画像反思 (Reflect)** 任务。

### 3.2 L2: 语义存档 (The Archive)
*   **索引单位**：会话片段（Session）。
*   **内容格式**：
    *   `Vector`: 对“会话摘要”进行 Embedding。
    *   `Payload`: `{"summary": "摘要文本", "raw_log": "原始对话原文", "timestamp": "...", "keywords": [...]}`
*   **优势**：检索摘要比检索单句话更精准，且返回原文能让 AI 获取最真实的语境。

### 3.3 L3: 用户画像引擎 (The Profile Engine)
*   **画像结构**：
    *   **基础信息**：称呼、职业、地理位置。
    *   **核心偏好**：喜欢的食物、关注的技术、对 Miku 的态度。
    *   **关键事实**：最近在做的项目（如“正在重构记忆系统”）、重要的经历。
*   **反思机制 (Reflection)**：
    *   调用 LLM 比较 `当前画像` 与 `最新 L1 对话`。
    *   指令：“提取新事实，修正过时信息，保持画像简洁。”

---

## 4. 关键流程 (Workflows)

### 4.1 写入与反思流程 (Background Path)
1.  **触发 Flush**。
2.  **生成摘要**：调用 API 对 L1 进行摘要提取。
3.  **向量存入**：将摘要存入 ChromaDB。
4.  **画像更新**：将 L1 内容喂给 LLM，输出更新后的结构化画像文本。
5.  **清空 L1**。

### 4.2 检索与生成流程 (Read Path)
1.  **用户输入**。
2.  **并行获取背景**：
    *   从 SQLite 获取 **L3 画像**（极快）。
    *   从 ChromaDB 检索 **L2 相关历史**（Top 3 摘要）。
3.  **注入 Prompt**：
    *   将画像置于 System Prompt 的核心位置。
    *   将 L2 检索到的历史作为 `## 往事回顾` 插入。
    *   将 L1 剩余内容作为 `## 最近对话` 插入。
4.  **LLM 生成回复**。

---

## 5. 显存优化策略 (Resource Management)

为了在当前 (5340MB / 6144MB) 的极端环境下运行：

1.  **全量 API 化**：
    *   **Embedding**: 严禁加载本地模型，强制使用 OpenAI 或其他兼容的远程 API 接口。
    *   **Summary/Reflection**: 使用高性能低成本模型（如 DeepSeek-Chat 或 GPT-4o-mini）。
2.  **实例按需加载**：
    *   仅在对话发生时加载该用户的画像文本（普通文本，占用内存极低）。
    *   不维持复杂的内存对象池。

---

## 6. 与现有系统集成建议

1.  **ChromaDB 改造**：在 `miku_memories` 集合中增加元数据标识，区分 `type=fact` 和 `type=session_summary`。
2.  **插件解耦**：在 `MemoryService` 中实现一套适配器，使得 `chat` 插件无需改动代码即可享受新的分层能力。
3.  **画像同步**：允许用户通过特定指令（如 `/whoami`）查看 Miku 对自己的画像记录，增加互动感。

---

## 7. 风险评估

*   **API 费用**：由于增加了摘要和反思的步骤，Token 消耗会略有增加。
*   **响应时延**：反思过程建议在后台异步完成，不阻塞当前的对话回复。
*   **画像漂移**：如果反思提示词写得不好，画像可能会由于单次对话的误读而产生偏差。需增加 `保存历史画像` 用于回滚。
